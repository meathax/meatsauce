# Gamma configuration before use

The full-window Preflight diagnosis (`.preflight/runs/20261010-024403/`, source fingerprint `e122bdf`) reproduced black output in both hostile seeds and localized the failure to `emu.hps_io.gamma_en`. Its scratch initializer patch passed. Earlier PLL and six-register attributions came from insufficient diagnostic windows and are superseded; the original reports remain retained.

`sys/hps_io.sv` does not initialize gamma enable. Command `0x32` updates it; `0x33` writes the lookup table. The standard mixer uses the enable directly. A random enabled state with an empty table can therefore replace a working board image with black output. The generated Preflight boot supplies neither command. This evidence localizes this failure to the platform video configuration, and does not establish that every real firmware configuration always initializes gamma enable.

[Main_MiSTer video.cpp](https://github.com/MiSTer-devel/Main_MiSTer/blob/master/video.cpp), inspected2026-10-10, writes R/G/B entries for each index with command `0x33`, then supplies the enable using `0x32` when loading a gamma curve. The default configuration and cached configuration can both be zero; do not assume every boot performs that upload. `sys/hps_io.sv` turns these entries into bank addresses `{channel,index}` with channel0/1/2. No framework source is modified here.

`rtl/n8080_gamma_guard.sv` starts with an invalid table and recognizes the complete ordered768-write transaction before allowing enable. Isolated or interrupted writes cannot arm it. It forwards all table writes unchanged; after a complete upload, enable/disable and subsequent updates retain the donor behavior. Game reset leaves the independently configured platform table intact. The guard adds eleven state bits and an enable gate in the existing board clock domain; actual utilization and timing still require reports.
