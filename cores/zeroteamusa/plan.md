# Zero Team USA — complete MiSTer implementation plan

Prepared 2026-10-04. This is the authoritative plan. Update `progress.md`
as work lands; do not maintain another competing roadmap.

## Outcome and scope

Build a working, faithful MiSTer core for **Zero Team USA (US), MAME
0.289 `zeroteam`, Seibu Kaihatsu/Fabtek 1993 V30 JAMMA PCB**. Reuse the
staged rmonic79 Raiden II/DX hardware implementation inside this fresh
MiSTer-devel template. Complete real CPU-driven boot, attract and gameplay
with graphics, protection, sound and controls **in Verilator first**.

**Quartus analysis/synthesis, fitting and static timing analysis run during
RTL development**, as explicitly requested on 2026-10-05. Establish and
maintain timing closure at the real clocks. RBF generation, deployment and
MiSTer testing remain exclusively in Phase 8 after the simulation gate.
The replacement global instructions of 2026-10-04 require an explicit user
request before any RBF build or rebuild. The earlier standing RBF build
authorization is revoked. MiSTer access remains authorized, and the final
simulation gate still precedes hardware work.

Scope is the US set first. Other Zero Team regional sets, New Zero Team,
the 2000 board, cheats and finished savestates are optional follow-up work,
not requirements that delay this core. Four-player capability, native
timing, standard MiSTer controls, DIPs, pause, high scores, scaling, screen
flip and appropriate CRT options are part of this implementation.

## Decisions that avoid wasted work

1. **Primary base: rmonic79 Raiden II**, with its integrated V30 `ucore`.
   Keep its bus, renderer and memory architecture intact until an actual
   target discrepancy requires a change. The spacestate base documents a
   V33 CPU adaptation with different bus timing; use its modular chips as
   alternatives, not an automatic replacement for the actual V30.
2. Cup Soccer is related hardware, with useful COP work and four-player
   references, but its 68000 board is not the same target PCB. Neither
   whole-wrapper transplantation nor a fresh CPU implementation is needed.
3. **32 MiB SDRAM + built-in DDR3** is the default platform. Preserve the
   selected donor's SDRAM CPU/tile and DDR sprite/sample paths initially.
   All target logical ROM regions fit within 32 MiB; a single-SDRAM rewrite
   offers no necessary bring-up benefit. Record runtime DDR use explicitly.
4. Start at the donor's **96 MHz core**, exact **8 MHz pixel CE** (divide
   by 12), **16 MHz V30**, **3.579545375 MHz Z80/OPL2**, **1.02272725 MHz
   OKI pin7-high clock**. Preserve the actual CPU enable/microstep contract.
   Do not transplant clock-enable multicycle constraints between CPU versions.
5. **512 × 282 total, 320 × 256 visible, 55.407801 Hz**, horizontal 4:3.
   Do not inherit Raiden II's 240-line crop or vertical orientation. PCB
   refresh notes and MAME's hand-tuned raster differ slightly; record that
   distinction, start from MAME's explicit raw timing, refine only from evidence.
6. Use scanline tile/sprite engines with buffered source RAM and real
   memory latency. DDR-backed ROM caches are not a whole-frame renderer.
   Keep MiSTer's scaler framebuffer separate from the game's drawing logic.
7. Replace **YM2151 + two OKIs** with **YM3812 + one OKI**. Reuse Raiden's
   actual JTOPL2 integration and shared sound protocol, correcting clocks,
   banking and samples to the Zero Team map. Sound/coin glue comes early.
8. Zero Team uses **SEI251**, a battery-retained cipher/key path, and
   discrete/PAL priority glue **instead of SEI360**. Copying Raiden II ROM
   names, sprite cipher, blend table or sprite priority rules is insufficient.
9. **MAME is incomplete here.** `MACHINE_NOT_WORKING`, a sort/priority TODO,
   and four undumped PALs are explicit evidence. Use documented MAME behavior
   as a baseline, but resolve its target blockers using US program uploads,
   donor COP microcode, observable state and public PCB/game references.
   Do not copy a known failure and call the implementation complete.

## Working rules and minimum evidence

- One active implementation branch, `develop`; local commits per completed
  phase. Preserve pristine donor checkouts. No pushing or publishing without
  a separate request. Keep `sys/` unchanged.
- Each copied module gets provenance: repository/commit, source path,
  original notice/license and local changes. Use the integrated dependency
  version until a concrete defect justifies an upstream change.
- Never patch game ROMs to skip protection or run a host CPU/COP instead of
  the synthesizable RTL to satisfy a completion gate. Temporary probes may
  isolate faults, but acceptance uses the actual target program and RTL.
- Use one reference capture fixture and one integrated Verilator executable.
  Reuse compiled objects, deterministic seeds and checkpoints. Trace only a
  bounded window around a mismatch; avoid full-run VCDs and repeated raw logs.
- Focused regression tests are for changed behavior, protocol boundaries or
  an actual bug. Do not test every resistor, regenerate every donor's history,
  build redundant software oracles, or rerun all unchanged chip benches.
- Report nonempty sprite/ROM inputs, actual PC/instruction progress and
  actual rendered/audio output. A blank matching frame, forced milestone,
  or copied screenshot is not evidence that the game works.
- Test modeled request/acknowledge, byte enables, wait states and realistic
  memory delays. A zero-latency ROM model alone cannot establish line budgets.
- Keep a minimal state inventory for checkpoint/debug RAM access. Ship
  savestates only later if needed; do not let their infrastructure dominate.
- Once a meaningful check passes, stop expanding it unless subsequent work
  changes the behavior it covers. Record commands, commit and result paths.

## Timing closure during RTL development

Use `scripts/check_timing.ps1` with Quartus 17 at `D:\q17`. Run analysis
and synthesis after synthesizable RTL/source changes; run fit and STA when
logic, memories, clocks, CDCs or constraints change or timing needs proof.
Batch related edits and reuse unchanged successful stages. `All` runs map,
fit and STA; `Synthesis` runs map; `Fit` runs fit plus STA; `STA` reuses the
existing fit. Explicit stage commands exclude the assembler and RBF.

Review actual clock definitions, setup/hold/recovery/removal slack, resource
usage and relevant unconstrained paths. Record source identity and reports
in `progress.md`. Closure requires valid constraints and nonnegative slack;
compile success alone is insufficient. Fix demonstrated paths at their
responsible layer and rerun the affected simulation if RTL changes. Do not
mask real paths with blanket false paths or slow the target clock to pass.
The current baseline is pending until these checks pass; keep that status
explicit. The simulation release gate still precedes RBF and MiSTer testing.

## Phase 1 — import the selected hardware and establish the simulation seam

1. Copy the minimum transitive source set from `raiden2-rmonic`: V30 `ucore`
   and HEX tables, CPU wrapper, shared RAM, COP, CRTC, tile/text/sprite/mixer,
   memory clients/arbiters and sound support. Add provenance at subsystem roots.
   Exclude shooter menus, logos, alternate games and optional savestate UI.
2. Use its hardware hierarchy behind `ZeroTeam.sv`, adapting to the fresh
   template's current port contract. Build a hand-maintained active `files.qip`;
   retire demonstration modules only after the new top references are coherent.
3. Keep hardware modules shared between synthesis and simulation. Add a
   simulation top that provides clocks/reset, deterministic HPS ROM/input
   transactions and SDRAM/DDR/RAM models. Replace only vendor primitives,
   not CPU, COP, audio or video logic, in the simulation path.
4. Resolve VHDL T80 via a reusable GHDL-to-Verilog artifact; if tool support
   is unavailable, select the staged TV80 equivalent with a focused IM0/latch
   check. Do not silently turn sound off to get Verilator compiling.
5. Create `sim/Makefile`, `sim/main.cpp`, source list and RAM/PLL primitives;
   expose PC, bus operations, COP command/fault, line counters and audio output.
   Use installed Ubuntu WSL for Linux tools and run build/test in that same
   environment. Explicitly invoke POSIX scripts through their interpreter.
6. Start `docs/STATE.md` and `docs/MEMORY_MAP.md` with actual active memories,
   mapped registers, ownership, latency and memory clients.

**One exit check:** compile the real hierarchy in Verilator, reset it and
observe instruction/bus activity from the target program. Fix compile,
missing asset and reset problems at their responsible layer.

## Phase 2 — exact target program, buses, early sound/coins and MAME fixtures

1. Implement `zeroteam_mem` exactly: RAM gaps, COP registers, direct
   sprite-register write at 0x68e, CRTC, sound at 0x700, DIPs 0x740,
   P1/P2 0x744, P3/P4 0x748 and system 0x74c. Use correct 16-bit masks.
2. Assemble the four program byte lanes into the V30 image; bank
   0x20000–0x3ffff with reset entry 1, fixed 0x40000–0xfffff, reset vector
   at the correct top-of-memory address and target vblank IRQ/vector semantics.
3. Establish an initial working Z80/T80 path: exact fixed/banked program
   image, 2 KiB RAM, main/sound pending flags, YM IRQ RST10 and main-command
   RST18 arbitration/acknowledges. Route all coin inputs through the sound
   interface so the game can leave attract later.
4. Run one MAME reference session for cold boot/attract and one scripted
   coin/start/play session. Save selected RAM, COP uploads/command operands,
   sprite lists, tile/palette DMA destinations, register/input events and
   a few reference screenshots/audio register events. Store script and seed.
5. Measure video write/latch timing in the play session before changing
   buffers. Cover attract-to-play plus busy combat (use 1800 frames for a
   combined write sweep where useful); repeat only if a state remains unobserved.
6. Inspect why vanilla `zeroteam` is marked not working: capture the first
   protection/sort anomaly and map it to source and US uploaded tables.
   If MAME cannot supply viable gameplay, keep the useful boot/device fixtures,
   document that limit and use ROM/donor evidence for the missing behavior.
   Do not make a broken MAME run the sole pixel/gameplay oracle.

**Exit:** correct reset/IRQ progression and ROM bank behavior; sound command
handshake and coin edges reach real CPUs; a small reproducible reference
fixture exists. No arbitrary CPU timeout substituted for a game milestone.

## Phase 3 — Zero Team protection, COP and sprite decryption

1. Feed actual US COP program uploads into the integrated interpreter.
   List commands/modes that the game executes during boot/attract/play;
   compare covered operations to `seibucop.cpp`, `_cmd.ipp` and `_dma.ipp`.
2. Implement/fix required integer math, signed arithmetic, collision result
   registers, BCD/itoa, PRNG contract, command completion and bus arbitration.
   Use donor alternatives only for the first unsupported or wrong operation.
3. Match tile/palette DMA address units, private buffers, palette brightness
   value/mode and source masks. Handle CPU/DMA simultaneous requests without
   reusing stale read data or acknowledging before the transaction completes.
4. Resolve Zero Team sort-DMA/sprite ordering from its actual sort RAM,
   lookup/parameter registers and command tables. Prefer the family donor's
   microcode interpreter over game-specific constant answers. Track all
   observable PAL/decode behavior in `docs/HACKS.md` if it is approximated.
5. Implement `zeroteam_decrypt_sprites` exactly for the first 4 MiB of
   interleaved sprite data, including correct word/bit ordering and address
   permutation. Preserve the upper erased region. A small compiled MAME
   function can supply the independent decrypted-file hash/reference.
6. Make the normal hardware download path perform equivalent decryption
   and establish the SEI251's expected retained key/reset state. The harness
   may cache a verified decrypted image for faster repeated runs, but first
   prove it equals the output of the same hardware loader path.

**Two focused checks:** whole populated sprite-region hash against the
reference cipher, and observed US COP operand/result sequences through the
actual RTL. Then continue the integrated CPU boot rather than building a
large standalone COP test suite. No permanent protection stubs remain.

## Phase 4 — target video through stable attract mode

1. Set tile reset banks BG/MG/FG/TX to 0/1/2/0; MAME's `bank_reset`
   argument order is BG/FG/MID/TX. Change ROM bounds, CRTC
   semantics, source buffers and private DMA destinations to target geometry.
   Preserve the measured latch/snapshot timing and DMA ownership.
2. Adapt the sprite renderer from SEI252-family behavior to Zero Team's
   SEI251 sprite layout, code range, flips, coordinates, wrapping, clipping,
   priority and RAM ordering. Keep scanline rendering and double line buffers.
3. Change the mixer for Zero Team's `init_zeroteam` priority sequence
   {-1,0,1,2,3}, actual blended-color table and xBGR555 palette semantics.
   Do not retain the Raiden II table just because most pixels look right.
4. Emit all 256 visible lines at fixed 8 MHz CE, correct blank/sync polarity,
   native raster and 4:3 presentation. Shift sync inside blanking rather than
   silently shrinking active picture to the shooter's 240-line window.
5. Compare a few discriminating scenes: US title/logo, text, a scroll scene,
   foreground/background overlap, mixed-priority sprites and a fade/effect.
   Use matched state/events, not arbitrary equal frame numbers when CPU
   timing and MAME differ. Explain any mismatch inherited from broken MAME.
6. Read line-completion counters under realistic shared-memory latency and
   contention. Optimize only an engine/cache that misses its measured line
   deadline; use JTFRAME alternatives only if the inherited architecture fails.

**Exit:** a real cold boot reaches the USA title and a repeatable attract
loop, with nonempty correct graphics, scrolling, priority/fades and no
missing lines. Save representative images plus the reproducible checkpoint.

2. Use one JT6295, correct input clock/pin7, 256 KiB voice content and

3. Mix mono OPL2 + ADPCM into both output channels with correct signed

4. Map four players' directions, three buttons, coin and start; service/test
   and target DIPs. Derive action labels from the game/manual or verified
   code/input observations; do not import Fire/Bomb/Auto-fire from Raiden.
5. Script coins, player starts, movement, attacks, jump/special combinations,
   simultaneous controls, death/continue and reset. Verify four-player join
   behavior in the target cabinet/DIP mode without synthesizing a new board.

**Exit:** attract music, coin/start effects and distinct gameplay samples
are audible and plausible; input changes make the real game respond for
each supported player. Use one integrated audio/input scenario, plus a
single timer/latch regression only if fixing one of those boundaries.

## Fault triage / resume contract

| Symptom | First bounded evidence | Responsible area |
| --- | --- | --- |
| No reset-vector instruction | Vector bytes, one transaction, CPU CE/reset | ROM lanes, map, CPU/bus handshake |
| Boot stalls after COP call | Last command/upload, operands/results, wait edges | COP interpreter / target command / DMA |
| Garbled sprites | Interleaved/decrypted image hash then one object | Cipher/lane order, SEI251 layout |
| Correct tiles, wrong overlaps | Same-state sprite order, palette and blend index | Sort DMA / discrete mixer priorities |
| Coin ignored / audio silent | Z80 PC, pending/IRQ vector, YM/OKI writes | Early sound program/bank/latch/coin path |
| Flickering / missing lines | Line count vs memory delays and shared contention | Sprite/tile pipeline or memory arbitration |
| Sim passes, board fails | Build timing/CDC/assets and exact observed build | Hardware integration before chip redesign |

On each resume: read `progress.md`, the current phase and the named evidence
only; preserve completed stages. On a verified reusable debugging cause,
append a dated canonical lesson using the global template and refresh its
topic index. Do not reopen the full lesson corpus or duplicate historical
lesson files. Stop only at actual completion or a concrete external input
that prevents further meaningful progress.
