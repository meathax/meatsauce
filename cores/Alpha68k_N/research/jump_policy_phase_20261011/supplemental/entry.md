## 2026-10-11 - Trace CPU bus direction before accepting observer data

Context: Alpha68k N/FX68K, source revision 6caf, passive native observers comparing real CPU read returns and writes with MAME.
Symptoms: A first-hit V2 review accepted point-read values from SIM_PORT_OUT; an earlier review even recommended replacing the original correct read signal. The labels were interpreted without tracing the CPU ports.
Verified cause: FX68K declares input iEdb and output oEdb. The pinned board connects .iEdb(mdin), .oEdb(mdout). Registered work_q/strip_q responses drive mdin; CPU strip writes consume mdout. Private wrapper aliases SIM_PORT_DATA=system.board.mdin and SIM_PORT_OUT=system.board.mdout. Thus DATA/data_in is CPU read return; OUT/data_out is CPU write data. Signal names alone did not establish direction.
Fix: Retract the erroneous returned-data acceptance while preserving the original reviews, sources, receipts and live workers. Keep read-return gates separate from physical score writes, input phase, execution ancestry and whole-array comparisons. The original Japan read observer was correct; do not replace it with the write signal.
Check/prevention: Trace actual CPU port declarations, board connections, response drivers, write consumers and every export alias. Then bind the intended read/write observation to its accepted transaction edge, address and instruction ancestry. A known ROM word or correctly observed write cannot prove the CPU's returned read value. Observer phase must be qualified separately from direction.
Limits: This is source-direction proof and an evidence retraction, not new gameplay/RAM acceptance. Recover a return only from a correctly paired retained accepted mdin/data_in event; otherwise leave that gate open. No source, worker, ROM, runtime or build change was required.
