# Physical memory transport

The production memory plan remains 24 MiB of live work/texture/framebuffer RAM in the 32 MiB x16 SDRAM module, with cartridge ROM in reserved onboard DDR3. This document records implemented transport and its limits; it does not claim integrated game acceptance.

## SDRAM adapter

`rtl/memory/cs_sdram_backend.sv` adapts the existing one-outstanding request/reply contract to the pinned, unchanged `donors/sdram/src_v/sdram_axi_core.v` (ultraembedded, GPL-2.0-or-later). Targets 1/2/3 map their 8 MiB offsets into physical byte ranges 0..8 MiB, 8..16 MiB and 16..24 MiB. The unused last 8 MiB remains available. The CPU RAM mirror is normalized by the board decoder before this adapter. Each accepted word has exactly one reply; payload remains owned until ready. Four byte strobes become the two SDRAM DQM beats. Zero-strobe writes reply without issuing a device write; unmapped, oversized or unaligned tokens reply with an error.

The donor uses four banks, 8192 rows and 512 x16 columns, sequential burst length two, CAS latency two, open rows, explicit precharge and periodic auto-refresh. `SDRAM_MHZ=86` conservatively rounds the 85.90908 MHz domain for donor integer timing arithmetic. Its inverted forwarded SDRAM clock and two input sampling registers require `SDRAM_READ_LATENCY=3` for read acknowledgement; the physical mode register remains CL2. The initial parameter 2 failed readback against independently scheduled CL2 pin beats. With 3, the identical physical timing model and expected-memory comparisons pass; neither read beats nor expected results were relaxed.

`sim/memory/sdram_model.hpp` operates exclusively on external SDRAM commands/edges. It models CL2/BL2 data, DQM, row/bank ownership, precharge, refresh, and tRCD/tRP/tRAS/tRC/tWR/tRFC/tMRD checks at the target period. Its current minimum cycle assumptions are tRCD/tRP/tWR/tMRD=2, tRAS=4, tRC/tRFC=6; the maximum allowed refresh gap is 720 clocks, and the measured maximum is 682. These assumptions and physical pin phase/board delays must be qualified against the installed SDRAM device for final hardware closure; a command model does not prove physical I/O margins.

Verification: `python -X utf8 scripts/sim.py sdram` passed 10922 mapped/masked/error transactions, 5459 BL2 reads, 5432 BL2 writes, 308 refreshes and 214089 clocks. Maximum request latency 9207 clocks includes power-up initialization. See `docs/simulation_sdram.json` for command, source hashes and exit status.

## Remaining integration

The adapter is not yet connected to `cs_boot_probe` or the production MiSTer wrapper. Connect the verified DDR ROM/BIOS loading and read adapter through the backend router; implement NVRAM/reset-vector storage, readiness/reset ownership and framework-domain handshakes. Connect the exact transport to the board simulation and replace random per-request memory delays with the physical SDRAM/DDR models. Measure CPU/GPU/scanout/audio deadlines under the original game's traffic before accepting attract or gameplay. Optimize bursts/caching only from measured demand, preserving coherency and source-qualified timing checks. Production PLL phase, pin constraints, actual memory-device timing and CDC remain final closure requirements. No RBF is generated by the checker.


## DDR ROM and loader adapter (2026-10-05)

`rtl/memory/cs_ddr_rom_backend.sv` implements the MiSTer Avalon DDR port. The current CrystalSystem wrapper drives DDRAM_CLK from clk_sys; sysmem takes this port clock into its HPS bridge, so the adapter uses the 85.90908 MHz board domain rather than inventing a second DDR domain. The eventual HPS ioctl ingress still requires explicit synchronization into this domain.

The staged cartridge is exactly 50331648 bytes and BIOS 131072 bytes. Cartridge target 4 uses byte base 0x30000000; BIOS target 0 uses 0x33000000. DDRAM_ADDR is a 64-bit-word address. One 64-byte cache line fills with eight independently valid DDR beats; every selected 32-bit CPU word comes from a completely published line. Commands hold address/count/data/strobes through DDRAM_BUSY. Masked 64-bit loader writes have their own handshake/completion, invalidate the ROM cache and acknowledge actual Avalon acceptance. Zero-mask writes issue no command. CPU ROM writes are ignored. Cart reads beyond 48 MiB return 0xffffffff; invalid targets, BIOS bounds and alignment return errors.

Reset invalidates the cache and suppresses replies. Already accepted DDR reads drain all remaining beats before a new owner can be accepted, including beats delivered during reset. This avoids treating an old response as a new request after reset. Loader traffic must hold the CPU board in reset during ROM replacement so its own cache cannot retain the old cartridge. Packing the actual ioctl stream and global board-reset sequencing remain integration work.

`python -X utf8 scripts/sim.py ddr_rom` passes 2568 read/ignored-write/error transactions, 275 masked loader operations, 2272 eight-beat bursts, 271 actual writes and 38475 busy clocks. Maximum request latency 133 clocks. Checks include actual physical write addresses/byte masks, complete line reuse, reload invalidation, readonly bounds and reset drain. The independent Avalon model uses 20..70-clock initial read latency, 1..4-clock beat intervals and deterministic variable busy; these are explicit simulation assumptions, not measured HPS guarantees.

`python -X utf8 scripts/check_timing.py --target ddr_rom --registered-interfaces --fit` passes every fully constrained corner at 11.640 ns: setup +3.532/+3.295/+7.793/+8.214 ns, hold +0.354/+0.336/+0.181/+0.165 ns. `docs/ddr_rom_timing_registered_fit.json` records current source/configuration hashes. This is isolated transport timing, not integrated board or production I/O closure. No RBF generated.
